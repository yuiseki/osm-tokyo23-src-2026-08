# osm-tokyo23-src-2026-08

Dataset: https://huggingface.co/datasets/yuiseki/osm-tokyo23-src-2026-08

A frozen cut of OpenStreetMap covering the 23 special wards of Tokyo, taken
from the planet file of 2026-08-31, and the code that rebuilds every database
it was measured in. This repository holds the code; the data is on the Hub.

A question about a city has an answer only against a stated snapshot. An
answer computed today against the live API is not reproducible tomorrow, so
here the snapshot is one file with a checksum and every tool that reads it is
pinned in a Dockerfile.

## Running it

Fetch the planet file first, then point the first script at it:

```sh
PLANET=/path/to/planet-260831.osm.pbf ./scripts/01_extract_bbox.sh
```

```sh
./scripts/01_extract_bbox.sh          # the only pass over the planet, ~26 min
./scripts/02_build_ward_boundary.py
./scripts/03_extract_tokyo23_pbf.sh
./scripts/04_verify.py
./scripts/05_load_postgis.sh
./scripts/06_start_overpass.sh
./scripts/07_export_parquet.py
uv run scripts/08_relayout_parquet.py
uv run scripts/09_verify_parquet.py
python3 src/publish.py                # dry run; --push to upload
```

```sh
uv run python -m pytest
uv run ruff check src tests scripts
```

Everything after the first step takes minutes. The planet read is the cost.

## The published Parquet is laid out, not just exported

07 writes the tables in whatever order PostGIS hands them over, with `way` as
bare WKB. Nothing in such a file says the numbers are EPSG:3857, and nothing
in it lets a reader skip anything: a bbox query against the polygon table
read all 12 row groups, 118 MB.

08 rewrites each table without changing a value in it, with the same code as
[osm-japan-src-2026-08](https://github.com/yuiseki/osm-japan-src-2026-08):

- Rows are sorted by the Hilbert index of the centre of each geometry's bbox,
  on a curve over the whole EPSG:3857 square, then by `osm_id`, then by the
  WKB bytes. No DOUBLE column is a sort key, because DuckDB 1.5.6 returns
  -0.0 as 0.0 from a DOUBLE used directly in ORDER BY.
- A `bbox` struct column (`xmin`, `ymin`, `xmax`, `ymax`, doubles, EPSG:3857
  metres, exactly `ST_Extent(way)`) is appended after the osm2pgsql columns.
- The `geo` key holds GeoParquet 1.1.0 metadata: `way` as the primary
  geometry, WKB, its geometry type and extent, `bbox` as its covering, and
  the CRS as the PROJJSON of EPSG:3857 from the PROJ database in DuckDB.
- Row groups are about 4 MiB uncompressed, sized from each table's bytes per
  row. This is the one number that differs from Japan, which uses 32 MiB.

The row group size was measured, not carried over. At 32 MiB the four tables
are 2, 3, 9 and 1 groups, and a box query reads most of each file. Groups kept
and bytes read on the polygon table, for a 1 km box around Tokyo station, from
the footer alone:

| target | groups | bytes read | footer | four files |
|---|---|---|---|---|
| 32 MiB | 4/9 | 74 MB | 69 KB | 211 MB |
| 16 MiB | 4/17 | 38 MB | 120 KB | 212 MB |
| 8 MiB | 5/34 | 23 MB | 227 KB | 213 MB |
| 4 MiB | 6/71 | 13 MB | 452 KB | 208 MB |
| 2 MiB | 6/141 | 7 MB | 863 KB | 219 MB |

Smaller keeps paying for small boxes, but each halving doubles the footer,
which a remote reader fetches before anything else, and at 2 MiB the files
grow by 5% and `planet_osm_roads` hits DuckDB's floor of 2,048 rows a group.
For a whole ward the gain has already flattened: Setagaya's bbox reads 54 MB
at 4 MiB and 49 MB at 2 MiB. 4 MiB is the point where the footer is still
under 0.3% of each file.

The CRS was not assumed. `05_load_postgis.sh` passes no `-l`, `-E` or `-G`,
so osm2pgsql uses its default EPSG:3857, and the numbers agree: Tokyo
station's node 2149761647 is (15558758.54, 4256850.67) in the export, which
the inverse projection turns into 139.766706, 35.6812546, the position in the
pbf.

A bbox query then filters on the covering fields, and DuckDB skips the row
groups whose statistics rule them out:

```sql
-- 1 km around Tokyo station, in EPSG:3857 metres
SELECT osm_id, name
FROM read_parquet('data/parquet/planet_osm_point.parquet')
WHERE bbox.xmin <= 15559415 AND bbox.xmax >= 15558190
  AND bbox.ymin <= 4257460  AND bbox.ymax >= 4256226
  AND amenity = 'cafe';
```

It pays on `planet_osm_polygon`, which is three quarters of the bytes: that
box keeps 6 of 71 groups (13 MB) instead of 12 of 12 (118 MB). It pays little
on the other three. `planet_osm_line` keeps 15 of 19 groups for the same box,
because 595 of its rows are more than 10 km across, nearly all of them route
relations (train, road, bus, subway, ferry), and, sorted by their centres,
they widen every group to most of the city. The card has the full table. The cost is the `bbox` column itself:
doubles barely compress, and the four files grew from 159 MB to 208 MB.

Because the files now declare their geometry, DuckDB reads `way` as
`GEOMETRY('EPSG:3857')`; `ST_GeomFromWKB(way)` is a type error against them
and `way` goes into spatial functions as it is.

09 checks the result against the export, table by table: the same 70 columns
in the same order, the same multiset of rows (count and hash digests over
every column, `way` as bytes, FLOAT as text so -0.0 stays -0.0), the Hilbert
order, `bbox` equal to `ST_Extent(way)` on every row, and the `geo` metadata
equal to what the data implies.

## No schema of our own

The tables are osm2pgsql's classic pgsql output, because that is the layout
models have read for fifteen years of web maps. A friendlier schema of our own
design would measure whether a model can read a novel schema rather than
whether it knows OSM and SQL.

`--hstore` is not optional. The style promotes 106 tags to columns, but
`opening_hours`, `start_date`, `building:levels` and `operator:en` are not
among them, and questions ask about all four.

The ward polygons are already in `planet_osm_polygon`, tagged
`boundary=administrative` and `admin_level=7`. No separate ward table is
needed, and none was added.

## Three engines, one answer

The same question answered in PostGIS, in Overpass, and in DuckDB over the
Parquet. Counting `amenity=cafe` nodes per ward, all 23 wards agree across all
three: Chiyoda 507, Shibuya 477, Minato 429, Setagaya 258, Arakawa 44.

## Which 23 wards

Administrative relations at `admin_level=7` inside 東京都 whose name ends with
`区`. Inside Tokyo that is exactly the 23 wards, and the `admin_level` guard
keeps out the wards of other designated cities, such as Yokohama's 中区.

The boundary is derived from the same snapshot as the data. An earlier cut used
a boundary a year older and lost `way/1553541361`, created on 2026-08-30. One
boundary way of Setagaya went missing, its ring stopped closing, Overpass
silently stopped generating an area for that ward, and
`area["name"="世田谷区"]` began returning zero with no error. File size, node
counts and every ward's place node all looked normal.
`scripts/04_verify.py` counts relation members for exactly this reason;
`docs/clipping-and-broken-rings.md` is the write-up.

Tama and the islands are not here. They are part of Tokyo but not of the wards,
and the islands would stretch the bounding box across 18 degrees of longitude.

## Traps worth knowing

The geometry is EPSG:3857. At Tokyo's latitude a Web Mercator metre is about
1.23 real metres, so distances come out long and areas long squared. Measured
properly, JR Shibuya station is 802.9 m from the edge of Yoyogi Park; read
straight off 3857 it is 991.0 m. Write `ST_Transform(way, 4326)::geography`.

The load uses osm2pgsql's defaults, without `-G`, so a multipolygon relation is
several rows sharing one negated `osm_id`. Yoyogi Park, `relation/19862716`, is
two rows. Aggregate before measuring it.

`wiktorn/overpass-api` has four of its own, all handled in
`docker/compose.yml` and `scripts/06_start_overpass.sh`: it exits after the
import unless `OVERPASS_STOP_AFTER_INIT=false`, its `/api/status` always
returns 502 while `/api/interpreter` answers fine, its database directory is
created `drwx------` so fcgiwrap cannot reach the dispatcher socket until it
is chmodded, and by default the dispatcher refuses a query identical to one it
just served, answering HTTP 200 with an HTML page that a JSON client reads as
a parse error. `OVERPASS_ALLOW_DUPLICATE_QUERIES=yes` turns that off, and
anything that re-asks the same question needs it.
